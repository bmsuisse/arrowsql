1. **P1 — GIL-held locking can deadlock the interpreter** — [src/getinfo.rs:24](src/getinfo.rs:24). `getinfo()` waits for the connection mutex while holding the GIL. If its running query is blocked by another Python thread’s transaction, that thread cannot acquire the GIL to roll back or cancel. Statement getters have the same pattern. Acquire contended locks inside `py.detach`, then construct Python objects after releasing them.

2. **P1 — `setinputsizes()` reads the wrong tuple fields, causing data loss** — [src/params/mod.rs:34](src/params/mod.rs:34). Python passes `(sql_type, c_type, size, scale)`; Rust reads indexes 1/2 as size/scale. A timestamp hint `(SQL_TYPE_TIMESTAMP, 0, 6)` consequently becomes scale zero and truncates fractional seconds. Decimal hints can instead be silently rejected. Read indexes 2/3 and report invalid hints.

3. **P1 — NULL type inference bypasses timeout and cancellation** — [src/statement.rs:295](src/statement.rs:295). `sp_describe_undeclared_parameters` runs with unlimited timeout and no cancellation handle. A schema modification lock can therefore hang parameterized execution indefinitely despite `cursor.timeout` or cancellation. Propagate the request’s timeout/cancellation options and preserve those errors rather than swallowing them.

4. **P2 — `executemany()` ignores parameter metadata** — [src/statement.rs:728](src/statement.rs:728). Python converts explicitly typed Decimal values to strings before calling Rust, expecting `paramInfos` to retain their numeric type. Rust re-infers VARCHAR instead. For example, `INSERT t(v) SELECT ? / 2` with `Decimal("1.25")` fails integer conversion instead of inserting `0.625`. Apply each `ParamInfo` during conversion.

5. **P2 — `executemany()` discards `OUTPUT` results** — [src/statement.rs:654](src/statement.rs:654). The batch path retains counts/errors but never installs returned metadata or rows. `INSERT ... OUTPUT INSERTED.guid` leaves `description=None`, preventing retrieval. This fails the existing upstream `test_executemany_uuid_output_sets_uuid_str_indices`. Preserve results or select a compatible execution path.

6. **P2 — Statement errors discard subsequent batch results** — [src/statement.rs:398](src/statement.rs:398). Default `BatchErrorMode::Abort` drains results after an error. With `SELECT 1; RAISERROR('boom',16,1); SELECT 2`, catching the `nextset()` error cannot recover the final result. Use `Continue` for SQL batches and add an error-between-results regression test.

7. **P2 — MARS draining bypasses the requesting cursor’s timeout/cancellation** — [src/statement.rs:370](src/statement.rs:370). Another cursor’s pending batch is drained before the requester publishes its cancellation handle or applies its timeout. An earlier `SELECT 1; WAITFOR DELAY ...` can thus stall a new execution despite its one-second timeout; cancelling the requester targets a missing/stale handle. Include draining in its execution budget.

8. **P2 — Large `executemany()` calls incur quadratic copying** — [src/statement.rs:642](src/statement.rs:642). Each 2,000-row prefix drain shifts all remaining row vectors. One million rows moves approximately 249.5 million row headers—about 6 GB on 64-bit systems. Consume an owning iterator in chunks instead.
