# Upstream bugs found by the common-issues suite

Each is an `upstream_bug` + strict `xfail` test asserting the correct behavior; the Rust port must pass them.

- **test_integers_bool_float.py::test_python_int_beyond_bigint_is_dbapi_data_error**: Python int outside [-2^63, 2^63-1] raises a bare ValueError ('integer ... is out of range for SQL BIGINT') from the driver before sending, not a PEP 249 DataError, so callers catching mssql_python.Error miss it. Marked xfail(strict=True).
- **test_integers_bool_float.py::test_nan_float_parameter_raises_data_error**: float('nan') bound as a parameter raises ProgrammingError with a garbled TDS message ('Syntax error or access violation ... RPC protocol stream is incorrect'). A data-value problem should be DataError. Marked xfail(strict=True). inf and -inf also raise ProgrammingError but are only asserted as mssql_python.Error in a passing test.
- **test_nulls_typing.py::test_none_param_into_varbinary_column_inserts_null[VARBINARY(10)] and [VARBINARY(MAX)]**: A None parameter bound to a VARBINARY column (single execute) fails with ProgrammingError 'Implicit conversion from data type varchar to varbinary is not allowed. Use the CONVERT function'. The NULL is bound as a character type. The correct behavior is to insert SQL NULL and read back None. Marked upstream_bug and xfail(strict=True).
- **test_nulls_typing.py::test_executemany_all_none_varbinary_column_inserts_nulls**: executemany where the VARBINARY column is None in every row fails with the same implicit varchar-to-varbinary ProgrammingError. Correct behavior is to insert two NULLs. Marked upstream_bug and xfail(strict=True).
- **test_row_access.py::test_underscore_column_name_is_not_shadowed_by_internals[_values|_mapping|_cursor]**: Row attribute lookup resolves driver internals (_values, _mapping, _cursor) before column names. SELECT 42 AS _values then row._values returns the internal value tuple [42] instead of 42 (same for _mapping -> RowMapping, _cursor -> Cursor object). row['_values'] works. Marked upstream_bug + strict xfail; the 3 parametrized cases are reported as xfailed on upstream.
- **test_multiple_results.py::test_rowcount_follows_nextset_onto_later_dml**: After nextset() moves onto a later INSERT/UPDATE/DELETE count slot, cursor.rowcount keeps the previous statement's value. Repro: 'INSERT (1 row); INSERT (3 rows); SELECT COUNT(*)' gives rowcount 1 before and after nextset (correct is 3). Similarly 'UPDATE (7 rows); DELETE (3 rows)' keeps 7 after nextset onto the DELETE. Marked strict xfail; it will XPASS-fail once upstream is fixed.
- **test_stored_procs.py::test_call_escape_with_return_value_marker**: The ODBC call escape with a return-value marker, `{? = CALL proc(?)}`, is rejected by upstream with ProgrammingError 'Invalid parameter type' when passed [None, 21]. With [21] alone it fails with 'COUNT field incorrect'. The procedure is valid and this is standard ODBC syntax. Marked upstream_bug and xfail(strict=True). The test asserts that the escape executes without error.
- **test_binary_guid.py::test_memoryview_param_binds_as_binary**: memoryview parameter is rejected with TypeError 'Unsupported parameter type'. PEP 249 BINARY covers buffer types, so it should bind as varbinary. Marked xfail(strict=True).
- **test_binary_guid.py::test_none_param_into_varbinary_max_stores_null**: Python None bound to a varbinary(max) or binary(n) column fails with 'Implicit conversion from data type varchar to varbinary(max) is not allowed'. None should bind as a typed SQL NULL. The same None into a uniqueidentifier column works. Reproduced with autocommit on and off. Marked xfail(strict=True).
- **test_binary_guid.py::test_invalid_guid_string_raises_dataerror**: An invalid uniqueidentifier string ('not-a-guid') raises ProgrammingError, not DataError (SQLSTATE 22018 is a data error). Upstream's own SQLSTATE table maps 22018 to DataError. Reproduced in both autocommit modes. Marked xfail(strict=True).
- **test_executemany.py::test_truncation_raises_data_error**: String truncation (SQLSTATE 22001) in executemany raises ProgrammingError upstream, but PEP 249 puts data errors under DataError, and numeric overflow in the same driver already raises DataError. The class is also unstable: the first execution of a given temp-table name in a process raises ProgrammingError and later executions raise DataError. The test uses a unique table name so the strict xfail is deterministic.
- **test_executemany.py::test_mixed_cjk_and_emoji_batch_fits_column**: A batch whose values mix a CJK string ('日本語') and an emoji ('😀😀') raises RuntimeError 'Input string exceeds allowed column size' in NVARCHAR(20), even though every value fits and each value inserts fine alone. RuntimeError is also not a DB-API exception class. Reproduces with fresh table names; ['日本語','ab'] succeeds, so it is specific to the emoji/CJK combination.
- **test_messages_errors.py::test_string_truncation_is_data_error**: String truncation (SQLSTATE 22001) surfaces as ProgrammingError with 42000 driver text instead of DataError. Marked xfail(strict=True).
- **test_messages_errors.py::test_nextset_skips_print_to_reach_next_result_set**: nextset() returns True when a PRINT, RAISERROR 10 or DML count sits between result sets, then fetch raises 'Invalid cursor state'. The correct behaviour is to skip to the next real result set. Marked xfail(strict=True).
- **test_unicode.py::test_nul_inside_string_survives_executemany**: executemany truncates a str parameter at the first embedded NUL ('x\x00y' stored as 'x'); execute() keeps the full string. Also reproduces for a single-row executemany.
- **test_unicode.py::test_executemany_mixed_ascii_and_cjk_batch_preserves_text**: executemany with a batch mixing ASCII-only and non-ASCII strings corrupts the non-ASCII values: '中' is stored as '?' in NVARCHAR. Uniform non-ASCII batches are fine.
- **test_unicode.py::test_executemany_emoji_with_ascii_row_preserved**: Same batch-mixing corruption for emoji: '😀a' next to 'plain' is stored as ':-Da'. Emoji alone in a batch of 1 or 2 emoji rows round-trips.
- **test_unicode.py::test_truncated_surrogate_pair_fetch_returns_code_unit**: CAST(N'😀' AS NVARCHAR(1)) makes the server return the lone high surrogate (2 bytes, D8 3D). Upstream fetchone raises UnicodeDecodeError ('utf-16-le' codec); fetchall returns '' on the first call. The correct behavior is a successful fetch returning '\ud83d'. The expected value is a judgment call.
- **test_unicode.py::test_lone_surrogate_param_raises_unicode_encode_error**: Passing a lone surrogate str ('\ud83d') as a parameter raises a generic RuntimeError from the pybind layer ('Unable to cast Python instance of type str'), not UnicodeEncodeError.
- **test_transactions.py::test_lock_timeout_on_uncommitted_insert_raises_operationalerror**: A lock request timeout (SQL Server error 1222) is reported with SQLSTATE 42000, which upstream maps to ProgrammingError ('Syntax error or access violation'). It is an operational condition and should raise OperationalError. Marked upstream_bug and xfail(strict=True).
- **test_wide_and_many.py::test_2101_parameter_error_message_names_the_cause**: 2101 qmark parameters raise ProgrammingError with the driver-side text 'COUNT field incorrect or syntax error', which names no cause. The server's text is 'too many parameters ... maximum of 2100'. Marked upstream_bug and xfail(strict=True). Separately, upstream garbles the 2098 error text: word-shuffled or dropped words, varying per process. Not tested, because it is nondeterministic and a strict xfail would flake.
- **test_timeouts_cancel.py::test_cross_thread_cancel_interrupts_running_statement**: Upstream has no public Cursor.cancel(). cursor.close() called from another thread while a statement runs (WAITFOR DELAY 8s) does not interrupt it: in 2 of 3 runs the process segfaults (SIGSEGV, rc -11); otherwise the close blocks until the statement finishes and the worker completes normally. Test runs in a subprocess so the crash cannot kill pytest. Marked xfail(strict=True).
- **test_large_values.py::test_null_parameter_into_varbinary_max_plain_insert**: An untyped None parameter is bound as varchar, so INSERT of NULL into a varbinary column fails with ProgrammingError 'Implicit conversion from data type varchar to varbinary(max) is not allowed'. Same for varbinary(10). Expected: NULL stores as NULL. Workaround that works upstream: CAST(? AS varbinary(max)) or CONVERT(varbinary(max), ?).
- **test_large_values.py::test_insert_4001_chars_into_nvarchar_4000_raises_data_error**: String truncation (4001 chars into nvarchar(4000)) is raised as ProgrammingError (SQLSTATE 42000) instead of DataError, and the class is not stable. On a freshly compiled statement text the driver raises ProgrammingError; when the same statement text was already compiled (server plan cache) it raises DataError (SQLSTATE 22001 'right-truncated'). Expected: DataError every time. The xfail test uses a unique table name so it always takes the fresh-compile path and fails deterministically.
- **test_large_values.py::test_max_string_keeps_trailing_nul_on_fetch**: Parametrized over nvarchar(max) and varchar(max). Trailing NUL characters are stored by the server (DATALENGTH and CAST to varbinary confirm it), but the driver drops them on fetch: 'x\x00' comes back as 'x'. Non-MAX columns (nvarchar(100), varchar(100)) keep the trailing NUL, and embedded NULs in MAX columns are preserved.
- **test_dead_connection.py::test_close_on_dead_connection_does_not_raise**: close() on a connection whose server session was KILLed raises OperationalError (Communication link failure). close() should be cleanup and not fail on a dead link. Judgment call: PEP 249 does not specify close() behavior on a dead connection. Marked upstream_bug + xfail(strict=True).
- **test_special_types.py::test_failed_xml_param_statement_keeps_session_temp_table**: A failed parameterized statement (here a malformed XML bind, but also any bind-conversion error such as int <- 'abc') drops the session's #temp tables. Same SPID, and the table is gone ('Invalid object name'). Raw T-SQL via sqlcmd keeps the temp table after the same sp_executesql failure. Strict xfail.
- **test_special_types.py::test_sql_variant_base_type_property_matches_stored_type**: In a multi-row result, SQL_VARIANT_PROPERTY(v,'BaseType') for a text row returns 'ar' instead of 'nvarchar' when it follows a row with a different-length value. Single-row reads are correct. Strict xfail.
- **test_special_types.py::test_sql_variant_text_after_other_length_row_keeps_full_value**: Multi-row sql_variant text values are corrupted when they follow a row of a different length: N'hello world' comes back 'helloworld' (space dropped), and 'abcdefghijklmnop' comes back 'klmnop'. Same root cause as above. Strict xfail.

- **test_rs_decimal_param_inference.py::test_executemany_38_digit_decimal_exact_roundtrip**: executemany rejects a fitting 38-digit Decimal (DECIMAL(38,6), 32+6 digits) with ProgrammingError 'Invalid precision or scale value', even for a batch of one. Plain execute with the same value round-trips exactly.
- **test_rs_decimal_param_inference.py::test_executemany_small_then_big_precision_row**: batch [Decimal('1.0'), 38-digit Decimal] into DECIMAL(38,6) fails with ProgrammingError 'Invalid precision value'. Batch precision is not derived from all rows.

- **test_rs_decimal_param_inference.py::test_executemany_float_first_then_decimal_mixed_batch**: batch [2.5, Decimal('1.25')] into a DECIMAL column raises RuntimeError 'Unable to cast Python instance of type float'. Single execute accepts float into DECIMAL.
- **test_rs_decimal_param_inference.py::test_executemany_decimal_first_then_float_mixed_batch**: batch [Decimal('1.25'), 2.5] into a DECIMAL column raises the same RuntimeError. Mixed float/Decimal batches fail in both orders.
- **test_rs_varchar_codepages.py::test_truncation_raises_data_error_consistently**: VARCHAR truncation (SQLSTATE 22001) on a VARCHAR column with a non-Latin1 collation raises DataError on the first failing insert per connection but ProgrammingError (server error 8152, 'would be truncated in table ... Truncated value') on later failing inserts. Same condition, different exception class; DataError is the PEP 249 class for it. Marked xfail(strict=True); fails with the ProgrammingError as expected.
- **test_rs_utf8_collations.py::test_executemany_wider_utf8_value_after_narrow_first_row_is_inserted**: executemany sizes the UTF-8 VARCHAR parameter buffer from the first row. A later 4-byte value (or any wider value) raises a bare RuntimeError('Input string exceeds allowed column size at parameter index 1') instead of inserting. Repro: executemany('INSERT INTO #t VALUES (?,?)', [(1,'a'),(2,'\U0001F600')]). Consistent across runs. Marked xfail(strict).
- **test_rs_utf8_collations.py::test_executemany_emoji_after_narrower_rows_is_not_silently_corrupted**: executemany with rows [(1,'ab'),(2,'\U0001F600'),(3,'x')] into VARCHAR(10) UTF8 stores row 2 as 2 bytes b':-' (DATALENGTH 2) with no error. Silent data corruption: the 4-byte character is truncated to the first row's buffer size and mangled. Marked xfail(strict).
- **test_rs_xml_deep.py::test_xml_null_param_after_str_param_same_statement**: Same cursor, same SQL text: execute 'SELECT CAST(? AS xml)' with a str, then with None. The second execute fails with ProgrammingError 'Implicit conversion from data type xml to varchar is not allowed'. The same NULL works on a fresh connection or cursor, and after executing a different statement, so a parameter type/binding from the previous execute appears to leak into the NULL parameter. Correct behavior: returns None. Marked xfail(strict=True).
- **test_rs_sql_variant_deep.py::test_datetimeoffset_in_variant_returns_aware_datetime**: A datetimeoffset stored in sql_variant is returned as a str ('2024-01-02 03:04:05.1234567 +05:30') instead of an offset-aware datetime, which is what a DATETIMEOFFSET column returns.
